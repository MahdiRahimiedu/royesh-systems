این سرویس مستقل برای مدیریت تجهیزات و ملزومات یک شرکت نرم‌افزاری است. از پوشه اصلی مخزن اجرا کنید:

```powershell
python -m uvicorn services.inventory.app:app --host 127.0.0.1 --port 8002
```

مستند تعاملی API: http://localhost:8002/docs و سلامت سرویس: http://localhost:8002/health.
نصب وابستگی‌ها، اجرای رابط وب، تنظیم PostgreSQL و استقرار در README اصلی مخزن توضیح داده شده است.

## پرونده‌ها و جریان کار

- `models.py`: جداول SQLAlchemy و محدودیت‌های دیتابیس.
- `schemas.py`: شکل درخواست‌ها، نوع داده و اعتبارسنجی سختگیرانه تعداد و مبالغ.
- `routes.py`: APIها و قواعد کسب‌وکار؛ هر عملیات فقط یک بار commit می‌شود.
- `seed.py`: داده‌های کاملاً فرضی برای ارائه دانشگاهی؛ اجرای مجدد داده موجود را بازنویسی نمی‌کند.
- `app.py`: اتصال سرویس، پایگاه داده، احراز هویت و مسیرها.

در تنظیم پیش‌فرض محلی، داده‌ها در `data/inventory.db` باقی می‌مانند. سرویس به اجرای سامانه پرسنلی یا بازرگانی وابسته نیست. شناسه و نام کارمند هنگام تحویل ثبت می‌شوند؛ این‌ها مرجع بیرونی و تصویری از نام در زمان تحویل هستند. تیم ادغام بعداً از API پرسنلی برای انتخاب و تأیید کارمند استفاده می‌کند.

## گردش خرید و موجودی

۱. تأمین‌کننده و کالا تعریف کنید. برای تجهیزات دارای هویت مستقل مانند لپ‌تاپ، `tracking_type=serialized` و برای اقلام تعدادی مانند کابل، `quantity` انتخاب کنید. روش رهگیری پس از ایجاد کالا قابل تغییر نیست.
۲. سفارش خرید با تعداد صحیح مثبت و قیمت واحد به تومان ثبت کنید؛ ابتدا `pending` است. سقف مبلغ کل هر سفارش ۱۰ به توان ۱۵ تومان است تا نمایش عدد صحیح در رابط وب دقیق بماند. هر سفارش سریال‌دار حداکثر ۱۰ هزار تجهیز دارد.
۳. سفارش را تأیید کنید؛ سپس دریافت را ثبت کنید. برای کالای سریال‌دار به تعداد دقیق سفارش، سریال یکتا لازم است. سفارش فقط یک بار دریافت می‌شود و موجودی و گردش ورود در یک تراکنش ذخیره می‌شوند.
۴. سفارش دریافت‌نشده را می‌توان لغو کرد. لغو سفارش دریافت‌شده یا بازگرداندن آن به حالت قبل مجاز نیست.

برای ورود اولیه بدون سفارش، از `POST /movements` استفاده کنید. در کالای سریال‌دار شماره سریال‌ها الزامی‌اند. `POST /assets` هم یک تجهیز اولیه همراه گردش ورود ایجاد می‌کند. برای کالای تعدادی، خروج مستقیم از `POST /movements` موجودی کل و قابل استفاده را کاهش می‌دهد. خروج مستقیم تجهیزات سریال‌دار مجاز نیست.

## تحویل، بازگشت و اسقاط

در `POST /assignments` دقیقاً یکی از `asset_id` یا `item_id` را بدهید؛ تجهیز سریال‌دار با `asset_id` و تعداد یک تحویل می‌شود. تحویل، موجودی قابل استفاده را کم می‌کند ولی مالکیت سازمان را تغییر نمی‌دهد. بازگشت از `POST /assignments/{id}/return` فقط یک بار ثبت می‌شود. بازگشت جزئی در این نسخه وجود ندارد؛ برای بازگشت‌های مستقل، تحویل را در چند ردیف ثبت کنید.

`quantity_total` تعداد تحت مالکیت سازمان، شامل تجهیزات تحویل‌شده است. `quantity_available` تعداد قابل تحویل در انبار است. اختلاف این دو، تعداد تحویل‌های باز است. برای کالای مصرف‌شده به‌جای تحویل قابل‌بازگشت، خروج مستقیم ثبت کنید.

سقف موجودی کل هر کالا یک میلیارد واحد است؛ این سقف در همان UPDATE شرط‌دار بررسی می‌شود تا جمع ورودهای متعدد هم در SQLite و PostgreSQL یک رفتار داشته باشد. اگر دریافت خرید از سقف عبور کند، وضعیت سفارش، گردش و همه تجهیزات جدید به‌صورت کامل برمی‌گردند و سفارش تأییدشده باقی می‌ماند.

تجهیز فقط وقتی موجود است (`available`) با `PATCH /assets/{id}` و `status=retired` اسقاط می‌شود. تجهیز تحویل‌شده ابتدا باید برگردد. تجهیز اسقاط‌شده مجدداً فعال نمی‌شود. همه عملیات گردش کالا ایجاد می‌کنند؛ تاریخچه حذف نمی‌شود.

## دسترسی و صحت داده

کارمند (`staff`) فقط فهرست و جزئیات کالا و داشبورد عمومی انبار را می‌خواند. کارشناس (`manager`) و مدیر (`admin`) عملیات انبار و گزارش موجودی را انجام می‌دهند. ایجاد حساب فقط برای مدیر است. تمام مسیرهای داده نیاز به Bearer Token دارند.

کاهش موجودی، تغییر وضعیت سفارش و قفل تجهیز با UPDATE شرط‌دار دیتابیس انجام می‌شوند؛ کنترل وضعیت و تغییر آن یک عملیات SQL هستند. در نتیجه درخواست همزمان نمی‌تواند موجودی را منفی، تجهیز را دوبار تحویل، یا سفارش و تحویل را دوبار پردازش کند. شکست اعتبارسنجی یا سریال تکراری کل تراکنش را rollback می‌کند.

پاسخ `409` برای تعارض وضعیت یا موجودی، `404` برای مرجع ناموجود، `422` برای داده نامعتبر و `403` برای دسترسی ناکافی است. فهرست‌ها صفحه‌بندی، جست‌وجو و در موارد مربوط فیلتر وضعیت دارند. جست‌وجو با پارامتر `q` انجام می‌شود؛ حداکثر اندازه صفحه ۱۰۰ است.

فیلترهای وضعیت و نوع گردش فقط مقادیر مستندشده را می‌پذیرند؛ مقدار ناشناخته پاسخ `422` دارد. جست‌وجوی اموال، تحویل‌ها و گردش‌ها با شماره سریال و کد کالا نیز کار می‌کند. `%` و `_` در متن جست‌وجو به‌عنوان حرف معمولی در نظر گرفته می‌شوند. ترتیب فهرست‌ها ابتدا تاریخ ایجاد نزولی و سپس شناسه نزولی است تا ردیف‌های هم‌زمان در صفحه‌بندی تکرار یا گم نشوند. همه زمان‌های پاسخ با منطقه زمانی UTC ارائه می‌شوند.

جست‌وجوی سریال در گردش‌ها، مقادیر واقعی آرایه JSON را می‌خواند؛ بنابراین سریال فارسی یا دارای نقل‌قول و بک‌اسلش با نمایش متنیِ escapeشده JSON اشتباه نمی‌شود. برای SQLite از `json_each` و برای PostgreSQL از `json_array_elements_text` استفاده می‌شود. حالت SQLite با آزمون بازگشتی بررسی شده؛ اجرای PostgreSQL در این محیط انجام نشده است.

داده نمونه با شناسه پایدار و علامت گردش اولیه شناسایی می‌شود. ویرایش نام کالا، کد کالا یا نام تأمین‌کننده باعث بازنویسی داده یا خرابی اجرای بعدی نمی‌شود. داده‌های قدیمی که شناسه تصادفی داشته‌اند نیز با علامت گردش اولیه شناسایی می‌شوند.

## بررسی صحت

از پوشه اصلی مخزن اجرا کنید:

```powershell
.venv/Scripts/python.exe -m pytest tests/test_inventory.py -q
```

آزمون‌ها فقط روی دیتابیس موقت اجرا می‌شوند و داده سامانه در حال اجرا را تغییر نمی‌دهند.

| بخش | رفتارهای بررسی‌شده |
| --- | --- |
| کالا و تأمین‌کننده | ثبت و ویرایش، نوع و طول داده، ایمیل، جلوگیری از تغییر موجودی از PATCH و تغییر روش رهگیری |
| خرید | تأیید پیش از دریافت، دریافت یک‌باره، لغو، برگشت کامل تراکنش نامعتبر و سقف مبلغ |
| گردش | ورود و خروج، موجودی منفی، سریال‌های لازم، سقف موجودی تجمعی، جست‌وجوی کد و سریال |
| تجهیزات | سریال یکتا، یک تحویل‌گیرنده، ویرایش توضیحات، اسقاط و ممنوعیت فعال‌سازی مجدد |
| تحویل و بازگشت | مانده قابل استفاده در مقابل مالکیت، بازگشت یک‌باره، فیلتر کارمند و وضعیت |
| گزارش و داشبورد | کمبود موجودی، مانده تحویل، صفحه‌بندی پایدار، فیلتر نامعتبر و UTC |
| دسترسی | تمام عملیات نوشتن برای کارمند و کاربر واردنشده رد می‌شوند؛ مدیر عملیاتی مجاز است |
| همزمانی | خروج همزمان، دریافت همزمان، تحویل همزمان یک سریال، رقابت لغو و دریافت |
| سازگاری داده | تطبیق مستقل مانده با گردش، تحویل باز و وضعیت تجهیزات؛ اجرای مجدد seed پس از تغییر نام و روی داده قدیمی |

## مرز نسخه

این سرویس دفتر کل مالی، استهلاک حسابداری، پرداخت به تأمین‌کننده و اتصال زنده به سامانه پرسنلی ندارد. اطلاعات نمونه واقعی نیستند. قیمت‌ها و تعداد در API عدد صحیح‌اند. داده حساس کارکنان در سرویس انبار کپی نمی‌شود.
