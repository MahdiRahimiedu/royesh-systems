# راهنمای مطالعه و ارائه پروژه

## از کجا شروع کنیم؟

ابتدا برنامه را اجرا کنید و از بخش پرسنلی، یک کارمند بسازید. سپس در مرورگر `/docs` همان سرویس را باز کنید تا ببینید یک فرم رابط کاربری در واقع با کدام درخواست HTTP کار می‌کند. منطق سامانه فقط در رابط نیست؛ اگر همان درخواست نامعتبر را مستقیم به API بفرستید هم رد می‌شود.

در Python، `models.py` شکل داده ذخیره‌شده را تعریف می‌کند. `schemas.py` شکل ورودی مجاز را مشخص می‌کند. مسیرهای `app.py` یا `routes.py` درخواست را دریافت، مجوز را بررسی و عملیات را انجام می‌دهند. در عملیات چندمرحله‌ای، فقط پس از موفقیت همه مراحل `commit` می‌شود؛ خطا باعث `rollback` است.

در React، `frontend/src/lib/resources.ts` ستون‌های جدول و فیلدهای فرم هر بخش را با نام‌های مشخص معرفی می‌کند. `ResourceForm` فرم ثبت/ویرایش و `ResourceTable` فهرست و جست‌وجو را می‌سازد. `workflows.ts` اقدام‌های وابسته به وضعیت را نگه می‌دارد. `api.ts` درخواست شبکه و خطا را یکدست می‌کند. نتیجه واقعی API مبنای به‌روزشدن رابط است.

## چرا سه دیتابیس؟

هر تیم باید بتواند ساختار و برنامه خودش را مستقل تغییر دهد. انبار نباید برای خواندن نام کارمند به جدول HR وصل شود. در این نسخه، شناسه مرجع را ذخیره می‌کند؛ تیم ادغام بعداً API پرسنلی را برای انتخاب و اعتبارسنجی کارمند متصل می‌کند. یکی‌بودن شناسه نمونه در سه سامانه جای ارتباط واقعی را نمی‌گیرد.

## تراکنش چه مشکلی را حل می‌کند؟

هنگام دریافت خرید، وضعیت خرید، موجودی، سریال‌ها و گردش انبار با هم تغییر می‌کنند. اگر یکی از سریال‌ها تکراری باشد، نباید بقیه تغییرات ثبت شوند. اگر دو کارشناس یک لپ‌تاپ را هم‌زمان تحویل بدهند، فقط یک عملیات موفق می‌شود. همین اصل برای وصول وجه و سقف صورتحساب‌ها اعمال شده است.

محاسبه حقوق از مقادیر همان لحظه نسخه ثبت‌شده می‌سازد. تغییر حقوق پایه ماه بعد نباید فیش صادرشده را عوض کند. دلیل وجود ستون‌های مبلغ در خود فیش همین است.

## سناریوی ارائه

1. با admin وارد پرسنلی شوید. یک واحد و کارمند ثبت کنید؛ تغییر وضعیت همکاری و پرونده را نشان دهید.
2. یک مرخصی بسازید، آن را تأیید کنید و تلاش دوم برای تصمیم‌گیری را امتحان کنید؛ API آن را رد می‌کند.
3. مأموریت ثبت و هنگام تأیید، فوق‌العاده مصوب را وارد کنید. تشویقی ثبت کنید، فیش دوره همان تاریخ را صادر و ریز محاسبات را نمایش دهید. مزایا و کسورات پیش‌نویس را اصلاح و سپس ثبت پرداخت را انجام دهید؛ فیش پرداخت‌شده قابل اصلاح نیست.
4. در انبار کالای سریال‌دار، تأمین‌کننده و خرید ثبت کنید. خرید را تأیید و سریال‌ها را هنگام دریافت وارد کنید.
5. تجهیز را به شناسه یک کارمند تحویل و سپس برگشت دهید. عملیات تکراری و موجودی غیرمجاز پذیرفته نمی‌شود.
6. در بازرگانی مشتری و پیشنهاد چندردیفی ثبت کنید. در پیش‌نویس یک ردیف را اصلاح کنید و جمع جدید را ببینید؛ ارسال/پذیرش را انجام دهید و قرارداد بسازید.
7. قرارداد را فعال، صورتحساب صادر و بخشی از مبلغ را دریافت کنید. مانده در گزارش مطالبات مشخص می‌شود.
8. با staff وارد شوید و تفاوت دسترسی‌ها را نشان دهید. در پایان OpenAPI و فایل‌های تحویل به تیم ادغام را معرفی کنید.

همه این داده‌ها برای نمایش دانشگاهی ساختگی‌اند؛ عملیات ثبت وجه در این محیط وجهی جابه‌جا نمی‌کند.

برای دیدن دامنه بررسی هر بخش، [ممیزی جامع امکانات](feature-audit.fa.md) را بخوانید. `check.cmd` آزمون‌های بک‌اند، آزمون منطق فرم و خروجی و نشست در فرانت‌اند و بررسی TypeScript را اجرا می‌کند. گزارش `artifacts/api-coverage.json` پس از pytest نشان می‌دهد کدام ترکیب مسیر و روش HTTP واقعاً پاسخ موفق داشته است؛ این گزارش پوشش خط‌به‌خط کد نیست.

## افزودن یک فیلد جدید

فیلد را به مدل SQLAlchemy و schema ثبت/ویرایش اضافه کنید. سپس یک migration Alembic بسازید؛ تغییر مدل به‌تنهایی ستون دیتابیس قدیمی را عوض نمی‌کند. آن را در فیلدها و ستون‌های resources.ts معرفی کنید، پاسخ API را بررسی و اگر قاعده تجاری دارد، یک آزمون معنادار برای آن بنویسید.

برای تغییرات API قرارداد تیم ادغام را به‌روز و `python scripts/export_api.py` را اجرا کنید. تغییر اسم فیلد مصرف‌کنندگان دیگر را می‌شکند، بنابراین ابتدا با تیم ادغام هماهنگ کنید.

## معنی خطاها

| کد | مفهوم | مثال |
| --- | --- | --- |
| 401 | ورود لازم یا نشست منقضی | توکن حذف‌شده پس از خروج |
| 403 | دسترسی کافی نیست | تأیید مرخصی توسط کارمند |
| 404 | رکورد پیدا نشد | شناسه قرارداد ناموجود |
| 409 | عملیات با وضعیت یا داده فعلی ناسازگار | تحویل دوباره یک تجهیز |
| 422 | ورودی معتبر نیست | پایان قبل از شروع، مبلغ منفی |
| 429 | تعداد تلاش ورود زیاد است | بیش از ده تلاش در یک دقیقه |

## محدودیت‌های شفاف

این تحویل برای یک شرکت نمونه و اجرای محلی ساخته شده است. چندسازمانی، ورود سراسری، بیمه/مالیات، حسابداری دوبل، تسویه بانکی و ادغام سه سامانه در دامنه فعلی نیستند. امکان انتقال روی سرور با تنظیمات محیط و دیتابیس PostgreSQL وجود دارد؛ آماده‌بودن تنظیمات به معنی انجام تست میزبانی یا انتشار واقعی نیست.
