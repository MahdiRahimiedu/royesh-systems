# تحلیل اولیه پروژه دانشگاهی مدیریت شرکت نرم‌افزاری

تاریخ: ۲۰۲۶-۱۰-۲۳ — وضعیت: دامنه اصلی تأییدشده؛ جزئیات نسخه اول پیشنهادی

## مبنای تحلیل و تصمیم‌های تأییدشده

درخواست کاربر: تحقیق، تحلیل و طرح پرسش‌های لازم پیش از شروع پیاده‌سازی؛ بک‌اند پایتون و فرانت‌اند React/Next.js.

تصاویر، منبع شرح تکلیف هستند. پیشنهادهای این سند الزام استاد محسوب نمی‌شوند.

- تصویر اول: معماری سرویس‌گرا/میکروسرویس، Client، API Gateway و سرویس‌هایی با پایگاه داده مستقل دیده می‌شود.
- کاربر تأیید کرد سامانه سوم «بازرگانی، مشتریان و قراردادها» است. این پاسخ مبنای طراحی است.
- کاربر تأیید کرد هر سه سامانه را می‌سازیم و اتصال نهایی با تیم دیگری است.
- در حال حاضر الزام خاصی برای ابزارها اعلام نشده است. خوانایی و قابل‌فهم بودن پروژه برای دانشجوها اولویت اصلی است.
- انعکاس نور و بریدگی بالای تصویر مانع رونویسی کامل و قطعی متن تخته است.
- استقلال سرورهای برنامه و API از توضیح کاربر مشخص است. الزام ماشین فیزیکی یا مجازی جدا هنوز مشخص نیست.

## سناریوی سازمان

یک شرکت توسعه نرم‌افزار سفارشی با تیم‌های توسعه، تست، پشتیبانی و مدیریت. کارکنان استخدام می‌شوند، تجهیزات شرکت را تحویل می‌گیرند و روی پروژه‌ها کار می‌کنند. تجهیزات شامل لپ‌تاپ، مانیتور، تجهیزات شبکه و اقلام مصرفی است. دارایی سریال‌دار و کالای تعدادی باید جدا مدل شوند.

## دامنه پیشنهادی نسخه اولیه

| سامانه | قابلیت‌ها | داده‌های اصلی |
| --- | --- | --- |
| پرسنلی | پرونده کارمند، واحد و سمت، قرارداد، استخدام و خاتمه همکاری، درخواست و تأیید مرخصی و مأموریت، حقوق ساده، تشویق و جریمه | Employee، Department، EmploymentContract، LeaveRequest،Mission، PayrollRecord، PersonnelAdjustment |
| انبار و تدارکات | تعریف کالا و دارایی، تأمین‌کننده، درخواست خرید، ثبت دریافت، خروج و برگشت، تحویل تجهیزات به کارمند، گردش موجودی و هشدار کمبود | Item، Asset، Supplier، PurchaseRequest، StockMovement، AssetAssignment |
| بازرگانی | مشتری، خدمت نرم‌افزاری، پیشنهاد قیمت، قرارداد پروژه، صورتحساب و وضعیت وصول | Customer، ServiceOffering، Quotation، ProjectContract، Invoice، PaymentRecord |

وجود entity در این جدول به معنی لزوم جدول مستقل نیست. اولویت‌بندی پیشنهادی در سند implementation-plan.fa.md ثبت شده است.

برای نسخه دانشگاهی، حقوق با فرمول آموزشی و قابل تنظیم محاسبه شود؛ تطبیق با بیمه، مالیات و قوانین استخدامی نیاز جداگانه‌ای است که فعلاً درخواست نشده است. ثبت دریافت وجه نیز از اتصال درگاه پرداخت جداست.

## مرز مالکیت داده

- پرونده کارمند و وضعیت استخدامی فقط در سامانه پرسنلی مرجع است.
- موجودی، گردش کالا و مالکیت/تحویل دارایی فقط در سامانه انبار مرجع است.
- بازرگانی مالک مشتریان و قراردادهای تجاری است. قرارداد استخدامی در پرسنلی با قرارداد تجاری پروژه تفاوت دارد.
- سایر سرویس‌ها با شناسه مرجع و API کار می‌کنند؛ اتصال مستقیم به جداول سرویس دیگر انجام نمی‌شود.
- سابقه کارمند یا دارایی دارای تراکنش حذف فیزیکی نمی‌شود؛ بایگانی یا تغییر وضعیت می‌شود.
- هویت کاربر برای ورود با پرونده کارمند یک مفهوم نیست. ورود مشترک و قرارداد نقش‌ها باید با تیم ادغام تعیین شود.

## معماری پیشنهادی

با توجه به تحویل مستقل به تیم ادغام، پیشنهاد به‌روز‌شده سه بک‌اند و سه رابط Next.js مستقل در یک مخزن است. هر سامانه باید بدون اجرای دو سامانه دیگر قابل نمایش باشد. سبک و الگوی کدنویسی سه سامانه یکسان خواهد بود.

ساخت دروازه، ورود سراسری، پنل مشترک و گزارش تجمیعی مسئولیت تیم ادغام است. تحویل ما شامل API مستند، راهنمای اجرا، داده نمونه و نقاط اتصال مشخص است. منطق استخدام، موجودی و قرارداد در سرویس مسئول خود باقی می‌ماند. رابط جست‌وجوی کارکنان در سامانه پرسنلی از نقاط اتصال پیشنهادی است.

استقلال سرویس الزاماً به معنی سه رایانه نیست. برای توسعه، سرویس‌های جدا در Docker Compose قابل اجرا هستند. برای ارائه، اگر استاد سه VM یا سه سرور جدا بخواهد، همان سرویس‌ها جدا مستقر می‌شوند.

پیشنهاد اولیه فناوری:

- FastAPI برای APIهای مستقل، با OpenAPI و مستندات تعاملی خودکار؛ گزینه مناسب برای محوریت ارتباط سرویس‌ها.
- در پیاده‌سازی، SQLite محلی با فایل مستقل هر سرویس برای اجرای بی‌نیاز از نصب دیتابیس انتخاب شد؛ PostgreSQL با دیتابیس و کاربر اختصاصی برای استقرار روی سرور پشتیبانی می‌شود.
- SQLAlchemy برای دسترسی به داده و Alembic برای تغییرات ساختار دیتابیس. مسیرهای معمول با کدنویسی همگام و خوانا پیاده شوند؛ استفاده از async صرفاً در صورت نیاز مشخص.
- Next.js و React با TypeScript برای رابط فارسی و راست‌به‌چپ؛ Next.js خود یک فریم‌ورک مبتنی بر React است.
- Docker Compose برای اجرای محلی مجموعه سرویس‌ها.
- الگوی پیشنهادی فعلی FastAPI است. مقایسه با Django در تحقیق اولیه انجام شده؛ برای یکدستی آموزشی، سه بک‌اند با یک الگو ساخته شوند.

در شروع، ارتباط HTTP/JSON و API نسخه‌دار کافی است. افزودن Kafka، Kubernetes یا تقسیم هر قابلیت به میکروسرویس مستقل، فعلاً نیاز اثبات‌شده‌ای ندارد.

## قرارداد مشترک پیش از توسعه

1. مسیر API مانند /api/v1 و فایل OpenAPI برای هر سرویس.
2. شناسه‌های مشترک مرجع، قالب تاریخ، واحد پول و قواعد ورودی.
3. تعریف نقش‌ها و نحوه انتقال و اعتبارسنجی هویت کاربر؛ کنترل دسترسی داخل هر سرویس نیز اعمال شود.
4. ساختار خطا، صفحه‌بندی، جست‌وجو و فیلتر.
5. مستندسازی خطای سرویس و مهلت پاسخ؛ تیم ادغام باید خطای سرویس را از موجودی صفر یا فهرست خالی تفکیک کند.
6. جلوگیری از ثبت تکراری برای عملیات حساس مثل تحویل تجهیزات؛ تکرار درخواست شبکه نباید دو خروج ایجاد کند.
7. ثبت رخدادهای مهم همراه عامل، زمان و شناسه پیگیری درخواست.
8. داده آزمایشی هماهنگ و روش اجرای مستقل برای تحویل به تیم ادغام.

دریافت هم‌زمان اطلاعات چند سامانه به معنی تراکنش اتمیک مشترک نیست. برای فرایندهای چندمرحله‌ای باید وضعیت عملیات و امکان بازیابی مشخص باشد.

## سناریوهای پذیرش

- پرسنلی: ثبت کارمند، قرارداد استخدامی و تغییر وضعیت همکاری؛ ارائه API اطلاعات حداقلی کارکنان به گروه ادغام.
- انبار: دریافت تجهیزات، ثبت تحویل با employee_id و ثبت برگشت؛ برای اجرای مستقل، شناسه نمونه مستند استفاده شود.
- بازرگانی: ثبت مشتری، قرارداد نرم‌افزاری، صورتحساب و دریافت وجه؛ مسئول قرارداد با employee_id مشخص شود.
- سناریوی پیشنهادی برای تیم ادغام: انتخاب کارمند از API پرسنلی در انبار، نمایش تجهیزات هنگام تسویه و نمایش مسئول قرارداد تجاری. اجرای سراسری این سناریو جزو تحویل فعلی ما نیست.
- کاربر فاقد مجوز نتواند حقوق دیگران را ببیند یا موجودی را تغییر دهد، حتی با فراخوانی مستقیم API.
- هر سامانه با پایگاه داده خود و بدون اجرای دو سامانه دیگر قابل اجرا باشد.
- تحویل دارایی سریال‌دار به دو نفر هم‌زمان و موجودی منفی باید در سرویس انبار رد شود.

## مراحل اجرای پیشنهادی

1. نهایی‌سازی شرح نیازها، نقش‌ها، Use Case و مدل داده هر سامانه؛ قرارداد API با تیم ادغام.
2. یک مسیر کامل داخل پرسنلی: ورود، ثبت کارمند و نمایش فهرست، همراه API و رابط کاربری؛ الگوی آموزشی دو سامانه دیگر از همین مسیر پیروی کند.
3. تکمیل قابلیت‌های اولویت‌دار سه سامانه و گردش‌های تأیید.
4. آزمون گردش‌های هر سامانه، دسترسی و موجودی، داده نمونه و مستندات ارائه؛ تحویل قرارداد API به تیم ادغام.

## پرسش‌های باز

- موعد تحویل و تعداد اعضای اجرایی چقدر است؟
- ارائه محلی کافی است یا اجرای آنلاین لازم است؟ فعلاً اجرای محلی مبنای پیشنهاد است.
- خروجی مورد انتظار استاد چیست: کد، اجرای آنلاین/محلی، ERD، UML، مستند API، گزارش، فیلم یا اسلاید؟
- رابط فارسی و راست‌به‌چپ، تقویم شمسی و مبلغ تومان تأیید است؟
- حقوق آموزشی کافی است یا محاسبات خاصی خواسته شده؟ چه قابلیت‌هایی حتماً در نمره لحاظ می‌شوند؟
- نقش‌های لازم و دامنه اطلاعات قابل مشاهده برای هر نقش چیست؟
- تیم ادغام قرارداد مشخصی برای ورود مشترک، نقش‌ها و شناسه‌ها دارد؟ تا زمان دریافت، قرارداد پیشنهادی و ورود مستقل هر سامانه مستند می‌شود؛ ورود سراسری ساخته نمی‌شود.
