# اجرای آنلاین و نگهداری

این پروژه در تحویل فعلی روی لپ‌تاپ بررسی می‌شود؛ فایل‌های استقرار برای انتقال به سرور آماده‌اند، اما انتشار عمومی خودکار انجام نشده است.

## پیکربندی

هر سرویس را در یک فرایند یا کانتینر جدا اجرا کنید. برای هرکدام دیتابیس PostgreSQL و کاربر اختصاصی بسازید. مقدار PERSONNEL_DATABASE_URL، INVENTORY_DATABASE_URL و COMMERCE_DATABASE_URL را با URLهای `postgresql+psycopg://...` تنظیم کنید. DATABASE_URL عمومی فقط برای کانتینر یک سرویس مناسب است، نه محیط مشترک سه سرویس.

روی دیتابیس خالی `SEED_DEMO=false` و ADMIN_PASSWORD یکتای حداقل ۱۲ کاراکتری قرار دهید. اگر دیتابیس قبلاً نمونه‌سازی شده باشد، تغییر این مقدار حساب‌های قبلی را حذف نمی‌کند؛ دیتابیس تولید را جدا و خالی بسازید. فایل env را در Git یا image قرار ندهید.

`BUSINESS_TIMEZONE` پیش‌فرض `Asia/Tehran` دارد. تاریخ تجاری، مانند امروزِ صورتحساب و معوقات، از این منطقه زمانی گرفته می‌شود؛ زمان‌های ثبت رویداد در API همچنان UTC هستند. مقدار نامعتبر منطقه زمانی در شروع برنامه خطا می‌دهد. دوره حقوق به شکل میلادی `YYYY-MM` باقی می‌ماند.

مهاجرت هر سرویس، با SERVICE همان سرویس، از ریشه اجرا می‌شود:

```powershell
$env:SERVICE = 'personnel'
.\.venv\Scripts\python.exe -m alembic upgrade head
```

برای تغییرات آتی مدل، revision صریح Alembic بسازید و قبل از اجرا پشتیبان بگیرید. create_all تغییر ستون‌های موجود را انجام نمی‌دهد. downgrade اولیه عمداً مخرب نیست و اجرا نمی‌شود.

اگر دیتابیس محلی قبلاً با اجرای برنامه ساخته شده و دقیقاً با مدل فعلی مطابقت دارد، برای وارد کردن آن به مدیریت مهاجرت از `alembic stamp 001` با SERVICE درست استفاده کنید؛ اجرای upgrade اولیه روی جدول‌های موجود خطا می‌دهد. روی دیتابیس ناشناخته یا دارای تفاوت schema، بدون تطبیق ساختار stamp نکنید.

## رابط‌ها و HTTPS

هر نمونه Next.js مقدار ROYESH_SYSTEM جدا دارد. کد مشترک یک بار build می‌شود و نمونه‌ها با `npm run start:personnel` و معادل دو سامانه دیگر اجرا می‌شوند. API_URL هر نمونه باید آدرس عمومی API شامل `/api/v1` باشد؛ راهنمای frontend/.env.example تنظیم دقیق آن را نشان می‌دهد. CORS_ORIGINS هر API باید دقیقاً originهای مجاز همان رابط‌ها را شامل شود.

با Nginx/Caddy یا reverse proxy میزبان، HTTPS و دامنه جدا یا مسیرهای مشخص تعریف کنید. پورت مستقیم دیتابیس عمومی نباشد. secret در متغیر NEXT_PUBLIC قرار نگیرد. میزبان و پورت قابل تنظیم‌اند؛ پیش‌فرض اجرای محلی loopback است.

## محدودیت‌های عملیاتی

مدل ورود مستقل است. محدودکننده ورود در حافظه هر فرایند قرار دارد؛ برای چند worker یا چند سرور، rate limit مشترک در reverse proxy یا سرویس مرکزی لازم است. نشست‌های منقضی را می‌توان دوره‌ای از جدول auth_sessions پاک کرد. ثبت عملیات محلی است و جایگزین سامانه متمرکز نگهداری رخداد نیست.

پیش از بهره‌برداری واقعی، سیاست پشتیبان/بازیابی، کاربران واقعی، گردش اصلاح اسناد مالی، الزامات حقوق و دسترسی، نظارت و آزمون بار را با سازمان تطبیق دهید. پیاده‌سازی فعلی سامانه حسابداری قانونی یا محاسبه حقوق رسمی نیست.

## پشتیبان

برای SQLite پیش‌فرض یا مسیر `DATA_DIR`، دستور `python scripts/backup.py` snapshot سازگار ایجاد می‌کند، حتی با اتصال فعال؛ کپی ساده فایل db در حال نوشتن قابل اتکا نیست. اگر URL دیتابیس صریح تنظیم کرده‌اید، این ابزار از کپی خودکار فایل محلی احتمالی صرف‌نظر می‌کند و اعلام می‌کند که باید ابزار متناسب با اتصال را به کار ببرید. برای PostgreSQL از pg_dump و بازیابی آزمایشی استفاده کنید. پشتیبان‌ها را بیرون از سرور اصلی و با دسترسی محدود نگه دارید.
