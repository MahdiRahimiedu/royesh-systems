# برنامه پیشنهادی اجرای سه سامانه

این سند پس از تأیید بازرگانی به‌عنوان سامانه سوم، مسئولیت ساخت هر سه سامانه و واگذاری اتصال نهایی به تیم دیگر تهیه شده است. معیار اصلی طراحی، قابل‌فهم بودن کد و مراحل اجرا برای دانشجویان است. این برنامه هنوز پیاده‌سازی نرم‌افزار محسوب نمی‌شود.

## ساختار تحویل

ساختار نهایی: یک مخزن و سه بک‌اند مستقل در services/personnel، services/inventory و services/commerce، هرکدام با README. کد فرانت‌اند در frontend نگهداری و در سه نمونه مستقل با تنظیم ROYESH_SYSTEM اجرا می‌شود؛ هر نمونه API، حساب و نشست خودش را دارد. ابزارهای محدود پایه در shared بازاستفاده شده‌اند. هیچ سامانه‌ای برای راه‌اندازی به دیتابیس سامانه دیگر وابسته نیست.

پورت‌های پیشنهادی توسعه:

| سامانه | بک‌اند | فرانت‌اند |
| --- | --- | --- |
| پرسنلی | 8001 | 3001 |
| انبار | 8002 | 3002 |
| بازرگانی | 8003 | 3003 |

در پیاده‌سازی، پیش‌فرض سه فایل SQLite برای نصب آسان روی لپ‌تاپ است. سه پایگاه داده اختصاصی PostgreSQL نیز با تنظیمات محیط برای سرور پشتیبانی می‌شوند. جدایی فیزیکی سرورها در صورت نیاز بعدی قابل انجام است.

## الگوی کد آموزشی

در هر بک‌اند، main.py نقطه شروع است؛ config.py تنظیمات، database.py اتصال، models مدل‌های دیتابیس، schemas ورودی و خروجی، routers مسیرهای API و services منطق تجاری را نگه می‌دارند. همه بخش‌ها از ابتدا پوشه خالی و لایه اضافی نمی‌گیرند؛ فایل‌ها هنگام نیاز ساخته می‌شوند.

- route درخواست را دریافت و پاسخ را برمی‌گرداند.
- schema داده ورودی و خروجی را تعریف و اعتبارسنجی می‌کند.
- service قواعدی مثل جلوگیری از موجودی منفی یا محاسبه حقوق را اجرا می‌کند.
- model ساختار ذخیره‌سازی را تعریف می‌کند.

استفاده از معماری مشابه در هر سه سامانه، نام‌های روشن، README فارسی و توضیح چرایی قواعد مهم ترجیح دارد. برای هر خط کامنت یا برای هر عملیات ساده لایه انتزاعی جدا ساخته نمی‌شود.

Next.js با TypeScript انتخاب پیشنهادی فرانت‌اند است. یک الگوی مشابه برای فهرست، جزئیات، فرم ثبت و پیام خطا در سه برنامه به کار می‌رود. زبان فارسی، راست‌به‌چپ و نمایش مبلغ تومان فرض‌های پیشنهادی‌اند، نه پاسخ تأییدشده کاربر.

## نسخه اول قابل ارائه

| سامانه | اولویت اول | پس از تکمیل پایه |
| --- | --- | --- |
| پرسنلی | کارمند، واحد و سمت، قرارداد استخدامی، تغییر وضعیت همکاری | مرخصی و مأموریت با تأیید، حقوق آموزشی، تشویق و جریمه |
| انبار | کالا، دارایی سریال‌دار، ورود و خروج، تحویل و برگشت تجهیزات، گردش موجودی | تأمین‌کننده، درخواست خرید، هشدار کمبود، خروج یا فروش تجهیزات مستعمل |
| بازرگانی | مشتری، خدمت، قرارداد پروژه، صورتحساب و ثبت دریافت | پیشنهاد قیمت، اقساط و سررسیدها، گزارش مطالبات |

ستون دوم نقطه شروع توسعه است؛ ستون سوم قابلیت‌های مرحله بعد همان نسخه است و حذف‌شده از دامنه محسوب نمی‌شود. ترتیب دقیق به موعد تحویل وابسته است.

خدمات شرکت شامل طراحی سایت، توسعه سامانه سفارشی و پشتیبانی است. فروش خدمات نرم‌افزاری در بازرگانی و گردش تجهیزات در انبار ثبت می‌شود. درخواست خرید و دریافت کالای انبار با قرارداد فروش نرم‌افزار دو فرایند مستقل‌اند.

## قواعد مهم

- کد پرسنلی، شماره سریال دارایی و شناسه UUID قرارداد در دامنه خود یکتا باشند؛ عنوان قرارداد می‌تواند تکراری باشد.
- کارمند غیرفعال و قرارداد خاتمه‌یافته سابقه خود را حفظ کنند.
- موجودی از گردش‌های ثبت‌شده به دست آید؛ ویرایش مستقیم عدد موجودی مسیر معمول کاربر نباشد.
- ثبت خروج، کنترل موجودی و ثبت تحویل در تراکنش داخلی انبار انجام شود؛ رقابت هم‌زمان نباید باعث موجودی منفی یا تحویل تکراری دارایی شود.
- حقوق آموزشی از حقوق پایه و مزایا و کسورات تعریف‌شده محاسبه شود؛ فرمول در راهنما نوشته شود.
- مبالغ با نوع عددی دقیق ذخیره شوند؛ واحد مبلغ در قرارداد API صریح باشد.
- کاربر معمولی فقط داده مجاز خود را ببیند؛ نقش مدیر/کارشناس هر سامانه تعریف شود. نام و تعداد نهایی نقش‌ها با نیازهای پروژه تطبیق داده شود.

## آمادگی برای تیم ادغام

تحویل هر سامانه شامل OpenAPI، نمونه درخواست و پاسخ، راهنمای ورود آزمایشی، داده نمونه، تنظیمات محیط و توضیح نقش‌هاست. مسیرهای پایه /api/v1 و /health پیشنهاد می‌شوند.

پرسنلی، اطلاعات حداقلی مانند id، کد پرسنلی، نام نمایشی و وضعیت همکاری را در API مجاز ارائه می‌کند. اطلاعات حقوق و پرونده محرمانه در این خروجی قرار نمی‌گیرد. انبار و بازرگانی، employee_id را به‌عنوان مرجع بیرونی نگه می‌دارند؛ به جداول پرسنلی وصل نمی‌شوند.

برای نمایش مستقل، شناسه‌های نمونه مشترک و مستند استفاده می‌شود. وجود این شناسه در حالت مستقل به معنی تأیید واقعی توسط پرسنلی نیست. تیم ادغام اعتبارسنجی مرجع و گردش چندسامانه‌ای را با قرارداد نهایی تکمیل می‌کند. اگر پیش از ادغام اعتبارسنجی برخط لازم شود، adapter ارتباط با API به‌صورت صریح به دامنه اضافه خواهد شد.

ورود مستقل هر سامانه برای ارائه محلی پیشنهاد می‌شود. سه ورود مستقل، ورود سراسری محسوب نمی‌شود. پیش از تحویل نهایی API، مدل هویت و مجوزهای موردنیاز گروه ادغام باید هماهنگ شود.

## ترتیب کار

1. نهایی‌کردن موجودیت‌ها، نقش‌ها و قرارداد پایه API.
2. ساخت یک مسیر کامل پرسنلی از دیتابیس تا فرم و فهرست کارکنان؛ مستندسازی اجرای آن.
3. ساخت پایه انبار و بازرگانی با همان الگوی خوانا.
4. تکمیل گردش‌های تأیید، حقوق آموزشی، خرید و پیشنهاد قیمت.
5. بررسی قواعد مهم، اجرای مستقل سه سامانه و تهیه بسته تحویل برای گروه ادغام.

API Gateway، ورود سراسری، گزارش یکپارچه و هماهنگ‌سازی فرایندهای چندسامانه‌ای در محدوده تیم ادغام قرار می‌گیرند.
